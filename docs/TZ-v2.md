# Техническое задание v2: платформа «Холст»

**Версия:** 2.1  
**Дата:** 2026-09-19 (обновление: дорожная карта фаз 0–4)  
**Статус:** актуальное ТЗ для разработки (заменяет «Окончательное ТЗ» как рабочий документ)  
**Основание:** сопоставление кода репозитория `holst`, README и документов в `docs/` с фактическим поведением приложения.

---

## 1. Цель продукта

**«Холст»** — локальное веб-приложение для **визуального планирования**: задачи и заметки на бесконечном полотне, связи между ними и отдельный режим просмотра **графа** связей.

Цель v2 — **сначала** довести до стабильного MVP то, что уже заложено в коде, **затем** по фазам вернуть цели из старого ТЗ (голос, ИИ, rich-редактор, экспорт, undo, несколько холстов, auth, offline, Kanban) — не как «вырезанное», а как **запланированные этапы** (см. §10).

---

## 2. Для кого и ключевые сценарии

### Персона (одна, без мультипользовательности)

**Планировщик / автор проекта** — один пользователь на одном компьютере или в локальной сети, без обязательной регистрации.

### Сценарии (ядро, 3 штуки)

| № | Сценарий | Ожидаемый результат |
|---|----------|---------------------|
| S1 | **Холст** | Создать задачу или заметку, перетащить, отредактировать текст, данные сохраняются после перезагрузки |
| S2 | **Связи** | Связать две задачи или задачу с заметкой (и заметки между собой), увидеть линии на холсте |
| S3 | **Граф** | Открыть режим «Граф», увидеть все узлы и рёбра, вернуться на холст |

Дополнительный сценарий **S4 (желательно в MVP, но после S1–S3):** поиск по заголовкам → переход к элементу на холсте.

## 3. Объём работ: MVP и перенос на фазы

> **Важно:** возможности из старого ТЗ **не отменяются** — они **не входят в MVP (фазы 0–1)**, но закреплены в дорожной карте §10 (фазы 2–4).

### 3.1. In-scope — MVP (фазы 0–1)

- Один общий холст (без `canvas_id` / нескольких досок в UI).
- CRUD задач (`/api/cards`) и заметок (`/api/notes`).
- Позиция, размер, z-index на холсте (Konva).
- Редактирование заголовка и содержимого через UI (панель редактора).
- Связи: `task_links`, `note_links` — API + отрисовка на холсте + отображение в графе.
- Проверка **циклов** только для направленных связей между **задачами** (depends_on и аналоги).
- Режим **GraphView** (Cytoscape): чтение тех же данных, layout, без дублирования узлов при повторном входе.
- Запуск через **Docker Compose**: PostgreSQL + backend + frontend (+ reverse proxy по необходимости).
- Базовый **поиск** по заголовку (можно без PostgreSQL tsvector в MVP).
- Загрузка **файлов** к задаче (опционально в MVP+: один сценарий «прикрепить файл», скачать через API).

### 3.2. Не в MVP — перенесено в фазы (цели продукта сохранены)

| Область | Целевая фаза | Почему не в MVP сейчас |
|---------|--------------|-------------------------|
| **Tiptap**, rich text, таблицы в заметках, interact.js | **Фаза 2** | Зависимости есть, в `src/` не подключены; сначала стабильный plain-редактор |
| Full-text search (tsvector), UX поиска с переходом на холст | **Фаза 2** | Сейчас `ILIKE` по title; tsvector — при росте контента |
| Файлы в UI, graph → canvas (клик по узлу) | **Фаза 2** | API частично есть; нужен UI и навигация |
| Подзадачи в UI (`parent_id`, сворачивание) | **Фаза 2** | Поле в БД есть; логика отображения — после MVP |
| **Undo/redo**, `event_log`, `/api/history/*` | **Фаза 3** | Таблица создаётся, запись и API не реализованы |
| **Multi-canvas** (`canvas_id`, `GET /api/canvas`) | **Фаза 3** | Задел в моделях; один холст в MVP |
| **PDF** (WeasyPrint), **Markdown**-export | **Фаза 3** | Зависимости/идея из старого ТЗ; эндпоинтов нет |
| **Kanban** как **режим** (не замена холста) | **Фаза 3** | В коде — canvas; Kanban — альтернативное представление тех же задач |
| **Auth**, multi-user, разграничение данных | **Фаза 4** | Нет в коде; нужен после multi-canvas и стабильного ядра |
| **Voice-stt** (Vosk), `/api/voice/transcribe` | **Фаза 4** | Контейнер есть; модель не в репо, frontend и nginx не согласованы |
| **ИИ** (Ollama / LM Studio, генерация в заметки) | **Фаза 4** | Нет кода; опционально после auth/voice по решению |
| **Offline**-сборка (vendored libs, сборка без интернета) | **Фаза 4** | Требует отдельной инфраструктуры артефактов |
| Gunicorn, `routers/` / `services/` (как в `Archtecture.md`) | **По мере роста** (2–3) | Сейчас монолит `main.py` — достаточно для MVP |
| Мобильная адаптация production-ready | **Фаза 2–3** | Desktop-first в MVP |
| WebSocket, real-time collaboration | **После фазы 4** | Не в текущей дорожной карте v2.1; возможное развитие |

## 4. Функциональные требования MVP

### 4.1. Холст

- Бесконечное полотно: pan (перетаскивание stage), zoom (колёсико).
- Типы элементов: **задача** (прямоугольник), **заметка** (другой стиль).
- Создание с панели инструментов; элемент появляется **без перезагрузки страницы**.
- Drag элемента → сохранение `x`, `y`, `z_index` через API.
- Выделение элемента (визуально); снятие выделения кликом по пустому месту.
- Порядок отображения по `z_index`; перетаскиваемый элемент — поверх остальных.

**Не в MVP:** сетка, snap, подзадачи-с «квадратиками», сворачивание иерархии.

### 4.2. Редактирование

- Боковая или модальная панель: заголовок + текстовое содержимое (plain text или простой JSON-массив — как сейчас в API).
- Сохранение → `PUT /api/cards/{id}` или `PUT /api/notes/{id}`.
- Удаление элемента из панели.

**Не в MVP:** WYSIWYG, встроенные таблицы и изображения в теле заметки.

### 4.3. Связи

- Создание связи из UI (минимум: выбор источника и цели или drag от «якоря» — конкретный UX на усмотрение реализации, но **обязателен** в MVP).
- Типы связей задач: `depends_on`, `blocks`, `follows`, `related_to` (хранить в `link_type`; в UI можно начать с одного типа + выбор в списке).
- Связи заметок: `linked_to` (двунаправленная семантика на уровне продукта; в БД — две записи не требуются).
- Удаление связи.
- Отрисовка линий на холсте для существующих `task_links` / `note_links`.
- **Задача → заметка:** через `task_links` с `link_target_type=note` (как в текущем API).

### 4.4. Граф

- Маршрут `/graph`: узлы — все задачи и заметки; рёбра — все связи.
- Layout (например `cose`); повторное открытие **не** дублирует узлы.
- Клик по узлу (фаза 2 MVP+): переход на холст с центрированием (можно отложить).

### 4.5. Поиск (MVP+)

- Поле в toolbar → `GET /api/search?q=…` → список результатов → выбор → выделение на холсте.

### 4.6. Файлы (MVP+, если успеваем)

- `POST /api/cards/{id}/files`, `GET /api/files/{id}/download`.
- Без прямой раздачи с диска минуя API (как в старом ТЗ — желательно; текущий код отдаёт URL `/media/...` — зафиксировать и не усложнять в v2).

## 5. Нефункциональные требования

- **Развёртывание:** `docker compose up --build`, приложение на `http://localhost` (nginx) или `http://localhost:3000` (frontend) + `http://localhost:8000` (API).
- **Данные:** PostgreSQL 16; миграции Alembic — **единственный** способ изменения схемы (отказ от параллельного `create_all` в продакшене — целевое состояние).
- **Безопасность MVP:** без auth; не публиковать PostgreSQL наружу; `.env` не коммитить секреты.
- **Производительность:** до ~500 элементов на холсте без заметных лагов (ориентир, не SLA).
- **Браузеры:** последние Chrome / Firefox / Edge, desktop.

## 6. Упрощённая архитектура (целевая для v2)

```
┌─────────────┐
│   Browser   │
└──────┬──────┘
       │ HTTP
       ▼
┌─────────────┐     ┌──────────────┐
│  Frontend   │     │   Backend    │
│  Vue 3      │────▶│   FastAPI    │
│  Pinia      │ API │   SQLAlchemy │
│  Konva      │     └──────┬───────┘
│  Cytoscape  │            │
└─────────────┘            ▼
                    ┌──────────────┐
                    │ PostgreSQL   │
                    └──────────────┘

Опционально: один контейнер nginx перед frontend+backend (как сейчас).
```

**MVP (фазы 0–1):** compose без обязательного `voice-stt` — меньше точек отказа при первом релизе. **Фаза 4:** вернуть `voice-stt` в стандартный compose и согласовать маршруты nginx ↔ сервис.

**Оставить две графические библиотеки** (Konva + Cytoscape) — уже в коде; объединение в одну библиотеку — **техдолг фазы 3+**, не блокер MVP.

**Backend:** один модуль приложения или постепенное выделение `routers/` без микросервисов.

**Удалить из активной разработки (архив):** корневой `main.py`, `trash/`, дубликаты `Canvas*.vue` после слияния одной версии.

## 7. Модель данных (как в коде, упрощённо)

| Сущность | Таблица | Назначение |
|----------|---------|------------|
| Задача | `tasks` | id (UUID string), title, content (JSON), x, y, z_index, width, height, parent_id (зарезервировано) |
| Заметка | `notes` | то же + `task_id` (опциональная привязка к задаче) |
| Связь задач | `task_links` | source_id, target_id, link_type, link_target_type |
| Связь заметок | `note_links` | source_id, target_id, link_type |
| Файл | `files` | task_id / note_id, filepath, mime |
| Журнал | `event_logs` | **фаза 3:** undo/redo и аудит действий |

## 8. API (контракт MVP)

Эндпоинты **реализованы** (поддерживать и стабилизировать):

| Метод | Путь | Назначение |
|-------|------|------------|
| GET | `/api/health` | Healthcheck |
| GET/POST | `/api/cards`, `/api/cards/{id}` | Задачи |
| PUT/DELETE | `/api/cards/{id}` | Обновление / удаление |
| GET/POST | `/api/notes`, `/api/notes/{id}` | Заметки |
| PUT/DELETE | `/api/notes/{id}` | Обновление / удаление |
| GET/POST/DELETE | `/api/task-links`, `/api/task-links/{id}` | Связи задач |
| GET/POST/DELETE | `/api/note-links`, `/api/note-links/{id}` | Связи заметок |
| GET | `/api/graph` | Узлы и рёбра для графа |
| GET | `/api/search?q=` | Поиск (простой) |
| GET | `/api/max-z-index` | Следующий z-index |
| POST | `/api/cards/{id}/files` | Загрузка файла |
| GET | `/api/files/{id}/download` | Метаданные / URL файла |

**MVP (фазы 0–1):** только перечисленные выше эндпоинты. **Будущие фазы:** `/api/canvas` (ф.3), export PDF/Markdown (ф.3), `/api/history/*` (ф.3), `/api/voice/*` (ф.4) — описать в отдельном приложении к TZ при старте соответствующей фазы.

**Соглашения:**

- В JSON заметки: поле привязки к задаче — `task_id` (legacy alias `card_id` допустим в backend временно).
- Ответы — JSON; ошибки — HTTP 4xx/5xx с `detail`.

## 10. Фазы поставки (дорожная карта 0–4)

Сводка: **фазы 0–1 = shippable MVP**; фазы 2–4 возвращают амбиции старого ТЗ **поэтапно**, без отмены функций.

| Фаза | Фокус | Ключевые deliverables |
|------|--------|------------------------|
| **0** | Стабилизация | Блокеры API/UI, EditorPanel, smoke-тесты |
| **1** | **MVP** | Холст + связи + граф (S1–S3), DoD §11 |
| **2** | Расширение UX и контента | Tiptap, поиск, файлы, graph→canvas, подзадачи |
| **3** | Структура и экспорт | Undo, multi-canvas, PDF/Markdown, Kanban-режим |
| **4** | Инфра и интеллект | Auth, voice-stt, ИИ, offline-сборка |

### Фаза 0 — Стабилизация

- [ ] PR с блокерами: заметки API, toolbar, static, z-index задач (если ещё не в main).
- [ ] Подключить `EditorPanel` (plain text / JSON content).
- [ ] Smoke-тесты API (pytest): cards, notes, health.
- [ ] Alembic как единственный путь схемы (план миграции с `create_all`).

### Фаза 1 — MVP (сценарии S1–S3, Definition of Done §11)

- [ ] UI создания/удаления связей (задачи, заметки, task→note).
- [ ] Cycle check для task → task.
- [ ] GraphView: без дублирования узлов при повторном входе.
- [ ] README и планирование опираются на **`docs/TZ-v2.md`**.

**Явно не входит в фазу 1 (но запланировано ниже):** Tiptap, undo, PDF, voice, ИИ, auth, multi-canvas, Kanban, offline.

### Фаза 2 — Редактор, поиск, файлы, иерархия

- [ ] **Tiptap** (или эквивалент): WYSIWYG в `EditorPanel`, сохранение в `content` (JSON).
- [ ] **Поиск:** UX в toolbar + при необходимости PostgreSQL tsvector.
- [ ] **Файлы:** загрузка/скачивание в UI (`/api/cards/{id}/files`, notes).
- [ ] **Граф → холст:** клик по узлу, центрирование и выделение элемента.
- [ ] **Подзадачи:** UI для `parent_id` (отображение/сворачивание — минимально жизнеспособный вариант).
- [ ] `docker-compose.dev.yml` или упрощённая инструкция из `DEVELOPMENT_SETUP.md`.
- [ ] Touch / мобильный UX — базовая пригодность (не полный parity).

### Фаза 3 — История, несколько холстов, экспорт, Kanban

- [ ] **Undo/redo:** запись в `event_logs`, API `/api/history/undo`, `/api/history/redo` (или эквивалент), Ctrl+Z / Ctrl+Y.
- [ ] **Multi-canvas:** `canvas_id`, `GET/POST /api/canvas`, переключение досок в UI.
- [ ] **Экспорт Markdown** и **PDF** (WeasyPrint): эндпоинты и кнопки export (как в старом ТЗ).
- [ ] **Kanban-режим:** альтернативное представление **тех же** задач (колонки); холст остаётся основным режимом, не «Kanban как ядро».
- [ ] Техдолг: рефакторинг backend (`routers/`, `services/`), опционально Gunicorn для prod.
- [ ] (Опционально) объединение Konva/Cytoscape — только если метрики оправдают.

### Фаза 4 — Auth, голос, ИИ, offline

- [ ] **Auth:** пользователи, сессии/JWT, привязка данных к user (подготовка к multi-user позже).
- [ ] **Voice-stt:** модель Vosk в образе/документации, согласование nginx (`/api/voice/`) и Flask `/transcribe`, кнопка 🎤 в редакторе.
- [ ] **ИИ:** локальная интеграция (Ollama / LM Studio) — генерация текста/задач по запросу, сохранение как заметка/карточка (scope уточняется при старте фазы).
- [ ] **Offline:** vendored frontend-libs, кэш pip/npm артефактов, документированная сборка без интернета (как в старом ТЗ).
- [ ] Полный **docker-compose** с `voice-stt` для prod-like окружения.

### После фазы 4 (не детализировано в v2.1)

- Real-time collaboration (WebSocket), теги, бэкапы холста, внешние интеграции — по отдельным решениям заказчика.

## 11. Критерии успеха MVP (Definition of Done v2)

1. Пользователь за 5 минут без инструкции: создаёт задачу и заметку, двигает их, редактирует текст, обновляет страницу — **данные на месте**.
2. Создаёт связь между двумя задачами — **линия на холсте и ребро в графе**.
3. Режим «Граф» открывается повторно **без дубликатов** узлов.
4. `docker compose up --build` поднимает db + backend + frontend; health backend — OK.
5. В репозитории **одно актуальное ТЗ** — `docs/TZ-v2.md`; старые документы помечены как архив.

## 12. Нецели (non-goals) — только для MVP (фазы 0–1)

- Не пытаться **одновременно** поставить в первом релизе всё из старого «Окончательного ТЗ» (это фазы 2–4, не отмена функций).
- Не добавлять **новые** контейнеры в MVP без необходимости (voice-stt — **фаза 4**, не «никогда»).
- Не требовать offline-install в MVP (цель **фазы 4**).
- Не рекламировать в README как «готово» то, что ещё не в коде — указывать **фазу** из §10.

**Не является не-целью продукта в целом:** голос, ИИ, Tiptap, PDF, undo, multi-canvas, auth, offline, Kanban — см. дорожную карту §10.

### Что **сохраняем** из старого видения (смысл, не буква)

- Бесконечный холст и визуальное мышление.
- Задачи и заметки как равноправные объекты на полотне.
- Связи и отдельный **граф** для обзора структуры.
- Локальный стек (Vue + FastAPI + PostgreSQL), без обязательного облака.

### Что **отложили** (не выкинули) и почему порядок такой

- **Voice / ИИ / offline / auth** — **фаза 4**: тяжёлая инфра и политики безопасности; в коде почти нет, в MVP не блокируют S1–S3.
- **PDF / Markdown / undo / multi-canvas / Kanban-режим** — **фаза 3**: опираются на стабильное ядро и модель данных; `event_logs` и WeasyPrint уже намечены в репо.
- **Tiptap / поиск / файлы / подзадачи / graph→canvas** — **фаза 2**: улучшают ежедневную работу после shippable MVP.
- **Старое ТЗ «всё сразу»** — заменено на **очередность**, чтобы не повторять разрыв «документы обещают — код не тянет».
- **Kanban** — не отменён: **отдельный режим** (ф.3), холст остаётся главным представлением; не путать с заменой canvas «с первого дня».
